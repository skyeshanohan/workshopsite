DO THIS · OPEN VS CODE ONCE
  1. Launch Visual Studio Code from your applications / Start menu (not a browser tab).
  2. If you see a welcome page, that is fine — leave it open for now.
  3. Click the top icon in the Activity Bar (files / two pages). That is Explorer.
  4. Open the menu Terminal → New Terminal. A panel opens at the bottom. That is where you type commands.
  5. Click inside the terminal panel so the cursor blinks, then paste or type the three version checks below and press Enter after each line.
QUICK CHECK · TERMINAL IN VS CODE

What you should see
Three version numbers. Prefer v22.x.x for Node to match Actions; v18+ is usually fine locally. If a command says “not found,” use the install links above, quit VS Code completely, reopen it, and try again.

Useful words

Repository (repo): project files plus history. Commit: a saved checkpoint. Branch: a named line of work. Pull request (PR): a review request before merging into main. Publish: make the site available at a web address.

DO THIS · ACCOUNTS
  1. In a browser, sign in at github.com ↗.
  2. In VS Code, click the account / person icon near the bottom of the Activity Bar (or Accounts in the gear menu) and sign in with the same GitHub account if prompted.
  3. Copilot is optional — if it is not ready, keep going without AI.
02
STEP 02 · CREATE A REPOSITORY

Create your repository.

You’ll create your own copy of the starter so you can change it and publish it from your GitHub account.

DO THIS · DOWNLOAD + OPEN IN VS CODE
  1. Open the Portfolio lab and click Download starter ZIP ↓.
  2. Find the ZIP in your Downloads folder (name includes portfolio-starter). Double-click it to extract. You should get a folder named my-resume-site.
  3. In VS Code: menu File → Open Folder… (Mac: File → Open… and choose the folder). Select the my-resume-site folder itself — not your Downloads folder, and not a single file inside.
  4. Click Open / Select Folder. If VS Code asks “Do you trust the authors of the files in this folder?”, choose Yes, I trust the authors.
  5. Click the Explorer icon (top of the Activity Bar). In the file list you should see package.json, src, and public. If you only see one nested folder, you opened one level too high — use File → Open Folder again on the inner my-resume-site.
DO THIS · CREATE AN EMPTY GITHUB REPO
  1. In your browser, open github.com/new ↗.
  2. Repository name: something simple like my-resume-site.
  3. Choose Public.
  4. Leave Add a README, license, and .gitignore unchecked. The starter already has files; adding those now causes merge conflicts later.
  5. Click Create repository.
  6. On the empty repo page, copy the HTTPS URL (looks like https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git). Paste it into a notes app for Step 3.

Do not push yet. First confirm the site runs on your computer in Step 3.

Why Public?

GitHub Pages for a normal project repository is free when the repository is Public. A Private repository usually cannot publish a free Pages site on a free student account.

Why this matters

Your repository will store the site and its history. You change it, review it, and publish it from your own GitHub account.

03
STEP 03 · RUN THE PROJECT

Run the project locally.

GitHub hosts the shared copy. In VS Code, you’ll open your local copy and run it before editing.

DO THIS · PREVIEW LOCALLY
  1. Confirm Explorer still shows package.json and src at the top level of the open folder.
  2. Menu Terminal → New Terminal. Click inside the bottom panel so you can type.
  3. Type or paste npm install and press Enter. Wait until it finishes (can take 1–2 minutes). Errors about network usually mean retry or ask the facilitator.
  4. Type or paste npm run dev and press Enter. Leave this terminal running.
  5. In the terminal output, find a line with http://localhost:4321 (or similar). Hold Cmd (Mac) or Ctrl (Windows) and click the link, or copy it into your browser.
  6. You should see the sample resume site. Keep that browser tab open.

The local address works only on your computer — it is not the public website yet. If the terminal is “busy” with npm run dev, open a second terminal with the + button in the terminal panel title bar before running Git commands.

Install project tools
npm install
Start the local preview

DO THIS · PUSH TO GITHUB
  1. Keep the preview running if you can: in the terminal panel title bar, click + to open a second terminal. Run the Git commands there. (If you only have one terminal, stop the preview with Ctrl+C — on a Mac that is still Control+C, not Command+C — then run Git, then start npm run dev again later.)
  2. Click inside the Git terminal so the cursor blinks. Confirm the prompt is inside your my-resume-site folder (you should see that name in the path).
  3. Run the commands below one at a time. Replace the uppercase placeholders with your GitHub username and repository name from Step 2.

Copy one command at a time. Use the HTTPS URL from your empty repository page.

1 · Start Git history
git init
2 · Stage the project files
git add .
3 · Inspect what is staged
git status
git diff --staged

Check for passwords, tokens, private files, or anything you do not want to publish.

4 · Make the first commit
git commit -m "Create my portfolio"
5 · Name the main branch
git branch -M main
6 · Connect your GitHub repository
git remote add origin https://github.com/YOUR-USERNAME/YOUR-REPOSITORY.git

Change both capitalized placeholders first.

7 · Send your files to GitHub
git push -u origin main
Git says “Author identity unknown”?

Git stores a name and email with each commit. These identify the commit author; they are not your GitHub password. For a public portfolio, consider using the GitHub noreply address shown in GitHub → Settings → Emails.

Set your commit name
git config --global user.name "Your Name"
Set your commit email
git config --global user.email "YOUR-GITHUB-NOREPLY-EMAIL"

Replace the placeholder with your GitHub noreply email, then retry the commit.

Push asks for a password / authentication failed?

GitHub no longer accepts your normal account password for git push over HTTPS. Use one of these options:

  1. Browser sign-in (easiest on many laptops): when VS Code or Git opens a browser window, sign in and approve access, then retry git push -u origin main.
  2. Personal Access Token: on GitHub go to Settings → Developer settings → Personal access tokens, create a classic token with the repo scope, then paste the token when the terminal asks for a password (username = your GitHub username).
  3. Ask the facilitator if you are stuck for more than a few minutes — do not force-push.

Personalize the portfolio.

Almost all content lives in one file: src/data/profile.js. Change that file, save it, and the local preview updates. Only include information you are comfortable making public.

One starter for everyone

Empty sections stay hidden. Fill coursework and projects now; add experience when you have it.

DO THIS · OPEN THE CONTENT FILE

  2. Click the arrow next to src to expand it, then data, then click profile.js. The file opens in the center editor.

Terminal shows SyntaxError after editing profile.js?

That usually means a missing or extra comma in a list such as coursework, activities, experience, or projects. Check these three things:

  1. Every object except the last one in a list ends with }, (comma after the closing brace).
  2. The last object in a list can end with } or }, — both are fine — but do not leave a lone comma with nothing after it.
  3. Strings use matching quotes: 'like this'.

Undo the last edit (Edit → Undo), save, and run npm run dev again. If it still fails, ask the facilitator before rewriting the whole file.

  3. Confirm your name, sections, and photo look the way you expect.

STEP 05 · REVIEW YOUR CHANGE

Branch, commit, and open a pull request.

Primary path: VS Code Source Control + GitHub in the browser. Terminal commands are optional at the end. A branch keeps this task off main until you review and merge.

Issue→Branch→Commit→Pull request→Merge
DO THIS · 1 · CREATE AN ISSUE (BROWSER)
  1. Open your repository on GitHub.
  2. Click the Issues tab, then New issue.
  3. Title example: Add a featured project card.
  4. In the body, list checks such as: honest project summary · working link · readable on a phone · no secrets.
  5. Click Create. Leave this tab open — you will link the pull request later.
DO THIS · 2 · CREATE A BRANCH (VS CODE)
  1. Look at the Status Bar (very bottom of VS Code). You should see main (or similar) on the left.
  2. Click that branch name. A picker opens at the top of the window.
  3. Choose Create new branch… (wording may be Create new branch from…).
  4. Type add-featured-project and press Enter. Confirm you are branching from main if asked.
  5. Check the Status Bar again — it should now say add-featured-project. Do not edit until this is true.

A branch is a separate line of work. Feature work stays off main until you review and merge.

DO THIS · 3 · MAKE THE CHANGE
  1. In Explorer, open src/data/profile.js again.
  2. Update one project (or add one) so it matches your issue — real title, summary, link if you have one.
  3. Save the file (Cmd/Ctrl+S).
  4. Refresh the local preview and confirm the change on desktop and a narrow window.
DO THIS · 4 · STAGE, COMMIT, AND PUBLISH (VS CODE)
  1. Click the Source Control icon in the Activity Bar (branch / fork icon; often shows a number badge).
  2. Under Changes, find profile.js. Click the file name once to open the diff (green/red lines). Read it — only your intended edits should appear.
  3. Click the + next to the file (or next to Changes) to Stage it. The file moves under Staged Changes.
  4. In the message box at the top of Source Control, type a clear message such as Add featured project card.
  5. Click Commit (checkmark). If VS Code offers to stage all files, only commit after you have staged the files you want.
  6. Click Publish Branch or Sync Changes / cloud icon (wording varies). Approve the browser/GitHub sign-in if prompted. This uploads your branch.

Staging selects what goes into the commit. Committing saves history on your computer. Publishing / syncing sends the branch to GitHub — that is when a pull request becomes possible.

DO THIS · 5 · OPEN AND MERGE THE PULL REQUEST (BROWSER)
  1. Refresh your repository on GitHub. Often a yellow banner appears: Compare & pull request — click it. If not: Pull requests → New pull request.
  2. Confirm base: main and compare: add-featured-project.
  3. Title: same idea as your issue. In the description, mention the issue (e.g. Closes #1 if your issue is #1) and list how you tested.
  4. Click Create pull request.
  5. Open the Files changed tab. Read the diff. Does it match your issue?
  6. If it looks right, open the Conversation tab and click Merge pull request, then Confirm merge. You can delete the branch when GitHub offers.

STEP 06 · PUBLISH THE SITE

Deploy and verify the live site.

GitHub Actions builds the site, and GitHub Pages publishes it. If the build fails, open the failed job and read the log before changing files.

01Your repositoryAstro source files
→
02GitHub ActionsInstall + build
→
03GitHub PagesLive website
DO THIS · ENABLE PAGES AND VERIFY
  1. On GitHub, open your repository. Confirm you are looking at the main branch (branch dropdown near the file list).
  2. Click the Settings tab (repo settings, not your profile settings). You may need to scroll the tab bar on a small screen.
  3. In the left sidebar, click Pages.
  4. Under Build and deployment → Source, open the dropdown and choose GitHub Actions. Save if GitHub asks. Do this even if an Actions run already started.
  5. Click the Actions tab. Open the latest Build and deploy portfolio (or similarly named) workflow run.
  6. If the first run failed because Pages was not enabled yet: open that failed run → Re-run all jobs.
  7. Wait until the run shows green / success.
  8. Return to Settings → Pages. Click the published site URL (often https://YOUR-USERNAME.github.io/YOUR-REPOSITORY/).
  9. Check the homepage, your photo (if you added one), one project link, and a narrow browser window.

The first deploy can take a few minutes. Feature branches do not publish this starter — merge to main first. If it fails, open the run, expand the failed step, and read the first clear error before changing files.
